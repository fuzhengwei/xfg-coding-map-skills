# 使用场景与场景化设计

代码地图不是单一产物：同一套引擎 + 数据结构，按场景换"素材来源、页签组合、badge 语义、TOUR 动线、卡片口径"，就能服务完全不同的目的。生成前先判断场景，再按本文件的场景配置执行。

## 场景速查表

| 场景 | 触发信号 | 素材来源 | 页签 | badge 语义 |
|---|---|---|---|---|
| S1 教学章节 | "生成 xfg-N-M 的全景图"、"课程章节图" | 章节 commit / 已有教程文档 | 全景+时序+流程 | 新增/调整/复用（相对上一章） |
| S2 迭代对比 | "这次迭代改了什么"、"v1.2 → v1.3 变更图" | `git diff` 两基线 | 全景+时序 或 全景+流程 | A新增/M修改/D删除（相对上个版本） |
| S3 需求蓝图 | "这个需求怎么做，给我开发导览"、"设计个方案图" | 需求描述 + 现有代码结构 | 全景+时序+流程（目标态） | 计划新增/复用既有/需调整 |
| S4 PR/评审讲解 | "帮我讲讲这个 PR"、"review 这条分支的改动" | PR diff | 全景+时序（聚焦变更子图） | 本PR新增/本PR修改/未动 |
| S5 架构 Onboarding | "新人入职看懂这个项目"、"画个架构总览" | 全量代码结构 | 全景（可单页签） | 分层标注（入口/领域/基础设施/外部） |

## S1 教学章节（范例即模板内置示例 xfg-2-1）

- **叙事结构**：装配 → 核心抽象（端口/SPI）→ 主链路 → 异常分支 → 组装收尾，TOUR 沿这条线走。
- **卡片口径**：每个新类一张卡，讲"定位 → 关键设计 → 坑"；测试类单独"测试"卡；pom/配置变化出"调整"卡；上一章复用的关键模型出一张"复用"卡收尾。
- **细致化建议**：每站 text 末尾给一个"思考题"或"动手验证"提示（如"把 apiKey 环境变量去掉再跑，观察未配 Key 分支"），把图变成练习手册。

## S2 迭代对比（开发迭代复盘）

- **素材采集**：`scripts/extract-diff.sh <repo> <baseline-ref> [current-ref]` 输出 name-status + numstat + shortstat；按插入行数倒序深入阅读前 N 个文件。记录真实基线（分支/HEAD/日期）写进 MAP_META.subtitle。
- **行为状态三分开**：已核对的当前行为 / 建议行为 / 已实施验证过的行为，不混写；未实施前改后描述一律是"建议"。
- **树**：只展开有变更的路径，未变更的包折叠为一行（b:'old'）；变更类标 A/M。
- **图**：全景图只画"变更模块 + 它们的直接依赖"，变更节点绿色、被影响但未改的节点灰色；时序图画核心变更链路（不是全量历史链路）。
- **卡片口径**：每卡三问——**为什么改（需求/bug 背景）→ 改了什么（数据结构/行为）→ 影响面（谁依赖它、有什么风险）**。改了什么必须可复核（类#方法 + 判断/输入输出变化），拒绝"优化了 xx"这类空话。风险点用 errc 红色节点或 ⚠️ 标注。
- **TOUR 动线**：先看数据/契约变更 → 再看服务逻辑 → 最后看边界（入口/对外协议），即"评审动线"。
- **细致化建议**：统计区 numstat 真实数字放 header stats；把"回滚方案"写进最后一张卡（回退到哪个基线、有什么数据迁移代价）。

## S3 需求蓝图（开发前设计——"跟着流程走就能实现出来"）

代码还没有，图是**目标态**。这是把地图当"开发施工图"用。**必须在副标题或末站明确标注"目标态/建议实现，非已实施"**，外部契约与未决边界放说明卡 notes，不写成已生效：

- **树** = 计划的类清单（全部 b:'new' + 复用的既有类 b:'old'），等于开发任务清单；每个 method 节点写"签名：职责"。
- **图** = 目标架构（全景）+ 目标交互（时序）+ 目标主流程（含预期分支）。
- **卡片口径** = 实现规格：每卡列出 **方法签名清单、依赖的类、要写的测试点、验收标准**（"跑通 xxx 即算完成"）。
- **TOUR 动线 = 开发顺序**：第 1 站建骨架（目录/模块），第 2 站定义契约（接口/值对象），第 3+ 站按依赖序实现每个类，末站联调验收。每站 text 写明 **实现要点 + 完成标志**。开发者跟着导航条从 1 走到 N，代码就写完了。
- **细致化建议**：
  - 卡片里给**预估工作量**（S/M/L），树徽标可加任务序号约定；
  - 时序图中的消息标注**依赖的技术点**（如"SSE 解析：jackson streaming"）；
  - 在末站卡里放"整体验收脚本/命令"（启动命令 + curl 示例 + 预期输出）。

## S4 PR / 评审讲解

- 范围最小：只画 PR 触及的子图；基线 = PR 的 base 分支（`extract-diff.sh <repo> origin/main HEAD`）。
- **卡片口径** = 评审视角：**改动意图 → 实现方式 → 评审关注点**（并发安全、边界条件、错误处理、测试覆盖是否够）。
- **细致化建议**：把"评审结论区"做成最后一张卡（✅ 建议合并 / ⚠️ 需修改 + 修改清单），TOUR 最后一站直接给结论。

## S5 架构 Onboarding

- 单全景页签即可（时序/流程可各留一张最核心的调用链）。
- 树按模块完整展开，badge 换成**分层语义**：入口层/领域层/适配层/外部依赖（复用 b 字段四色）。
- **卡片口径** = 每模块"职责一句话 + 关键类 3 个 + 改动高频区"。
- **TOUR 动线** = 一次典型请求的生命周期：入口 → 领域 → 基础设施 → 返回。
- **细致化建议**：补一张"环境与启动"卡（怎么跑起来、配置在哪），新人第一件事是跑通，第二件事才是读懂。

## 通用质量红线（任何场景）

1. `validate-map.js` 0 错误才能交付；有 Chrome + Node 22+ 时 `render-map.mjs` 真渲染验收也必须通过，渲染失败不许声称 PNG/SVG 已生成。
2. 图里每个 🆕 节点都应该能通过某个树节点的 kw 联动到；树里每个 doc 节点都应该能在图里高亮。
3. TOUR 是"最小完整路径"——只看导览也要能理解全貌，自由探索是加分项。
4. 一张图讲一个主题。两个不相干的需求不要塞进同一张图，宁可生成两张。
5. 迭代更新用同一份数据源重新生成全部派生文件，保留稳定编号；不积累互相矛盾的"最新版"。
